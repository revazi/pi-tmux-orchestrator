# Pi Tmux Orchestrator 0.11.1

Version 0.11.1 replaces catalog-wide dynamic worker selection with exact
operator-approved worker pools. It builds on 0.11.0 without changing ordinary
static starts or the five-command Pi surface.

## Highlights

- Strict external root configuration v5 / `workerCandidates` v1 defines one
  approved all-role pool and optional replacement built-in role pools. Exact
  run/project/global provider/model locks and trusted custom-role bindings remain
  authoritative.
- Direct TypeSafe Jev and Pi fallback planning enforce identical per-role scope
  and canonical capability validation against Pi's available/scoped models.
- Planning-v2 admission binds pool policy, source/count, role eligibility, exact
  assignments, and canonical candidate facts. Post-preview drift fails closed;
  retained planning provenance contains bounded metadata and digests, not
  configuration bodies.
- Planning confirmation shows bounded pool source/count; final confirmation and
  the immediate start acknowledgement show exact provider/model/thinking
  assignments and bounded pool metadata.

## Breaking change

**Dynamic starts only:** `/or-start --plan`, model-tool `dynamicPlan=true`, and
terminal `--dynamic-plan` no longer silently offer the full available catalog.
Configure approved pools or lock every planner-eligible role to an exact
provider/model identity. An unlocked role without a pool fails before a provider
call with `approved_worker_pool_required` and migration guidance. Packaged model
defaults and thinking-only settings do not count as operator approval.

Static/manual starts require no pool; existing configuration versions 1–4 remain
supported. Retained planning-v1 records in manifests v8/v9 remain readable but
cannot authorize a new launch. Generate a fresh planning-v2 preview after
migration. No manifest or broker protocol migration is required.

## Upgrade safely

1. Finish or explicitly stop active runs before replacing the package. Preserve
   the external configuration and the original installation until those runs are
   safely finished or stopped; do not resume in-flight runs across versions.
2. Resolve exact available provider/model IDs with `/or-models`. Migrate the
   external `~/.pi/agent/tmux-orchestrator.json` (relative to `PI_CODING_AGENT_DIR`
   when set), or the absolute `PI_TMUX_ORCHESTRATOR_CONFIG` path. Retain existing
   fields, change the root `version` to **5**, and add `workerCandidates` with
   nested `version` **1**. Replace the synthetic IDs below with approved exact IDs:

   ```json
   {
     "version": 5,
     "workerCandidates": {
       "version": 1,
       "all": [{ "provider": "provider-a", "model": "exact-worker-a" }],
       "roles": {
         "reviewer": [{ "provider": "provider-b", "model": "exact-review-worker" }]
       }
     }
   }
   ```

   `all` is required. Each pool has 1–32 exact identities; at most five built-in
   role pools and 100 distinct identities are allowed. A role pool **replaces**,
   rather than extends, `all`. No globs, aliases, ranking, thinking, credentials,
   endpoints, or extra fields belong in pool entries. All configured identities
   must be available within Pi's current model scope, even if a lock overrides a
   pool or its role is not selected. Exact run/project/global locks may select
   an available identity outside a pool; custom roles keep fixed trusted
   bindings. The decision model is resolved separately and does not expand
   worker approval. Natural-language guidance cannot create approval.
3. **Fully locked alternative:** omit `workerCandidates` and keep a supported
   version 1–4 configuration (or v5 without pools), supplying authoritative exact
   provider/model locks for every planner-eligible built-in role. Optional roles
   the planner might select must also be locked or explicitly disabled. Eligible
   custom roles retain their fixed bindings. Thinking-only overrides and packaged
   defaults are insufficient; no catalog fallback is allowed.
4. Update and restart Pi:

   ```sh
   pi update npm:pi-tmux-orchestrator
   ```

   For a fresh install or exact-version reinstall, use
   `pi install npm:pi-tmux-orchestrator@0.11.1`.
5. Open `/or-dashboard`, press `d` for an explicit configuration check, and create
   a fresh dynamic preview. Review pool source/count and exact assignments before
   separately confirming launch. Policy, availability, or capability changes
   after preview require a new preview; a stale preview starts nothing.

See the full [approved-pool migration guide](https://github.com/revazi/pi-tmux-orchestrator/blob/v0.11.1/references/usage.md#approved-exact-worker-model-pools)
and [public migration announcement #202](https://github.com/revazi/pi-tmux-orchestrator/issues/202).

## Dashboard and commands

The command surface remains `/or-dashboard`, `/or-models`, `/or-start`,
`/or-send`, and `/or-stop`. Older `/orchestrator-*` aliases and separate
list/status/help/about/doctor/watch/attach slash helpers were removed; use the
five short commands and dashboard controls instead. Supervisor/restart remain
CLI or model-tool operations, not slash commands.

Dashboard controls: arrows or `j`/`k` select a session; Enter watches/attaches to
that exact session from inside tmux; tmux prefix then `L` returns to Pi. `d` runs
bounded doctor on demand, `r` refreshes, `x` requests explicit exact-session stop
confirmation, `?` shows help, and `q`/Escape closes. Opening or refreshing does
not automatically run doctor or start background polling. Start and stop
confirmations remain mandatory; interactive send uses a unique private message
file and does not expose its text in arguments or metadata.

## Profiles and exact per-project configuration

The packaged `economy`, `balanced`, and `thorough` profiles are deterministic
thinking-level maps, not provider/model selections. `thorough` remains the
compatibility default; profiles cannot alter tools, role authority, required
review, routing, or budgets. Dynamic planning still enforces its `medium`
thinking cap and model-specific support.

Strict external configuration supports exact existing canonical project
`directory` mappings for profiles, exact model defaults/role overrides,
single/phased flow, specialists, and other documented settings. No globs,
parent-directory matching, symlinked entries, or project-local policy files are
accepted. Model precedence remains explicit run role/all override → exact-project
role/default → user-global role/default → packaged fallback for static starts;
dynamic starts require exact approval instead of treating the packaged fallback
as a lock. Project policy cannot grant trust, add writers, or remove review.
See [profiles and exact project policy](https://github.com/revazi/pi-tmux-orchestrator/blob/v0.11.1/references/usage.md#profiles-and-exact-project-policy)
for schema, precedence, and examples. Keep credentials and endpoints out of this
configuration.

## Compatibility and safety

- Supported baseline: Pi 0.87.1, Python 3.11+, tmux 3.2+ (3.5+ recommended),
  macOS or Linux; Node 22.19+ for the npm package.
- Older retained manifests remain readable. New ordinary manifests remain v5,
  explicit custom-role manifests v7, and dynamic manifests v8/v9, over `broker-v1`.
- Exactly one built-in implementer writes; independent built-in review is
  mandatory. Built-in and custom specialists remain read-only.
- Tmux hosts workers/controllers; the authenticated private broker transports
  workflow messages. Durable broker state stays metadata-only; private task,
  report, provider, and configuration bodies do not enter it.
- Planning is opt-in with separate planning-call and launch authorization.
  Cancellation, invalid candidates, stale previews, and planner failures launch
  nothing. Jev transport remains fixed-endpoint, fail-closed, and without retries.
- Provider-free checks establish local mechanics, not production-wire acceptance,
  npm-registry installation, or verified rollback. No model quality, recency, or
  cost-saving claim is made. See the
  [prerelease acceptance workflow](https://github.com/revazi/pi-tmux-orchestrator/blob/v0.11.1/references/prerelease-testing.md#automated-provider-free-planning-gate).

## Rollback

If migration is blocked, finish or stop active runs, remove the new package,
reinstall the exact prior **0.11.0** release, and restart Pi:

```sh
pi remove npm:pi-tmux-orchestrator
pi install npm:pi-tmux-orchestrator@0.11.0
```

Restore the preserved prior configuration if needed. Do not resume an in-flight
run across package versions; keep its original installation until safely finished
or stopped. Review the [0.11.0 release notes](https://github.com/revazi/pi-tmux-orchestrator/blob/v0.11.0/releases/v0.11.0.md)
for prior behavior. These are operator rollback instructions, not a claim of
connected rollback verification.
