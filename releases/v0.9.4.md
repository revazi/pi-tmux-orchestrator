# Pi Tmux Orchestrator 0.9.4

Version 0.9.4 fixes post-approval implementer repairs so follow-up work always
has a broker assignment and passes through mandatory review again.

## Breaking change

There is no protocol, command, configuration, database-schema, or authority-model
breaking change in 0.9.4. The change applies to new broker processes started
from this package version; retained runs remain readable.

## Upgrade safely

Finish or stop active orchestrations, update the package, and restart Pi:

```bash
pi update npm:pi-tmux-orchestrator
```

Start a new orchestration after restarting. An already-running broker keeps the
code loaded when that run started and does not hot-reload this correction.

## What changed

- An authenticated operator message sent to the implementer after workflow
  approval now queues the latest run state and message without triggering an
  unassigned provider turn.
- The broker advances exactly one round and creates a real `implementation`
  assignment before the implementer acts.
- The resulting implementation report follows normal specialist activation and
  mandatory reviewer routing; approval cannot silently cover later changes.
- Retry with the same command ID remains idempotent and cannot create duplicate
  rounds or assignments.
- Messages to other roles and sends during an active or `needs_attention`
  assignment retain their previous steering semantics.
- Operator-message bodies remain outside SQLite, status, Supervisor metadata,
  and dashboard output.

The report guard still correctly rejects `orchestrator_report` when no active
assignment exists. This release fixes the broker transition that previously
allowed post-ready implementer work to reach that invalid state.

## Rollback

If needed, finish or stop active 0.9.4 runs and install the previous exact
version:

```bash
pi remove npm:pi-tmux-orchestrator
pi install npm:pi-tmux-orchestrator@0.9.3
```

Report problems through
[GitHub Issues](https://github.com/revazi/pi-tmux-orchestrator/issues).
