# Pi Tmux Orchestrator 0.12.0

Version 0.12.0 adds bounded worker recovery, more explicit opt-in planning, and
optional static provider-call admission. Ordinary static starts keep one writer,
mandatory independent review, and the same five slash commands. Dynamic planning
and call enforcement remain opt-in; no cost or quality improvement is claimed.

## Highlights

- Structured worker attention makes blocked, clarification, tool-failure, and
  report-failure settlements actionable. One private report reminder permits at
  most one additional provider request; reconnect/restart cannot renew it.
- Model-tool stop/restart/abort and exact session naming expose bounded recovery
  controls. Stop and restart require separate exact-run confirmation; uncertain
  acknowledgements are not completion, and duplicate restarts do not respawn.
- Independently select dynamic `topology`, `models`, and `thinking` scopes.
  Unselected axes remain locked to effective policy. Preflight confirmation shows
  the exact accessible/scoped worker identities and supported thinking through
  `max`; this is supported functionality, not a new default thinking setting.
- Explicit `change|investigation|review|advisory` intent distinguishes change
  orchestration from a direct parent answer. Non-change intent redirects or
  cancels without launching workers; no advisory workflow was added.
- Accepted-plan evidence exposes exact supplied non-secret candidate facts,
  bounded Choice confidence/probability and alternatives, and fixed/unavailable
  authority. Provider composition and materially supported homogeneous choices
  are checked within the same one authorized call. Heterogeneous unlocked
  model/thinking support uses a lossless joint tuple Choice when it fits.
- Optional static provider-call ceilings use durable broker reservations before
  dispatch, conservative restart-retained counting, fail-closed abort, and
  operator-only allowance extensions. Exhaustion pauses an incomplete assignment;
  an extension never automatically resumes it or bypasses required review.

## Breaking change

**Dynamic starts only:** new previews enforce task-intent, provider-composition,
and support contracts. When both final compositions are feasible, a homogeneous
plan needs a material capability or declared-catalog-cost advantage applicable to
all selected roles. Unsupported, inconsistent, stale, malformed, or oversized
plans fail before launch rather than silently choosing another plan. Revise
constraints, supply exact locks, explicitly choose static/manual planning, or
cancel. This does not claim mixed providers improve outcomes.

Existing 0.11.1 approved worker pools and supported external configuration
versions remain valid; there is no mandatory configuration rewrite. Static starts
and their defaults are unchanged. Users coming from before 0.11.1 still need
root config v5 / `workerCandidates` v1 approved pools or exact authoritative
provider/model locks for every planner-eligible role, including optional roles
not explicitly disabled. Packaged defaults and thinking-only settings are not
approval. See the [pool migration guide](https://github.com/revazi/pi-tmux-orchestrator/blob/v0.12.0/references/usage.md#approved-exact-worker-model-pools).

Retained historical records remain readable, with unavailable evidence labeled
rather than reconstructed. Fresh previews use planning v7/evidence v3 for
rectangular support and v8/evidence v4 for joint tuples. Finish or stop active
runs before upgrading and generate a fresh preview; never resume an in-flight
run across package versions.

## Upgrade safely

1. Finish or explicitly stop active runs. Preserve external configuration and the
   original installation until those runs are safely finished or stopped.
2. Keep valid 0.11.1 configuration. If upgrading from an earlier version, configure
   approved pools or fully lock every eligible role as described above. Use
   `/or-models` for exact available IDs; do not infer capability from names.
3. Update and restart Pi:

   ```sh
   pi update npm:pi-tmux-orchestrator
   ```

   For an exact-version installation after publication:

   ```sh
   pi install npm:pi-tmux-orchestrator@0.12.0
   ```

4. Open `/or-dashboard`, press `d` for an explicit configuration check, and create
   a fresh preview. Review intent, selected scopes, exact assignments, evidence,
   and pool source/count. Authorize the optional planning call separately from
   final launch. Changed policy/catalog/resource bindings require a new preview.
5. Leave call enforcement disabled unless explicitly wanted. Enabling it requires
   exactly Pi **1.4.0**, supported OpenAI completions/responses **SSE**, provider
   retries disabled, explicit run/role/assignment ceilings, and separate launch
   approval. Dynamic enforcing starts reject before a paid preflight. Read the
   [call-ceiling guide](https://github.com/revazi/pi-tmux-orchestrator/blob/v0.12.0/references/usage.md#opt-in-enforcing-provider-call-ceilings-static-starts)
   before use. Uncovered Pi versions/transports and auxiliary compaction/cache
   warming are not permitted in enforcing mode.

## Dashboard and commands

The five commands remain `/or-dashboard`, `/or-models`, `/or-start`, `/or-send`,
and `/or-stop`. For installations older than 0.11.0:

| Old command | Use in 0.12.0 |
|---|---|
| `/orchestrator-dashboard` | `/or-dashboard` |
| `/orchestrator-models` | `/or-models` |
| `/orchestrator-start` | `/or-start` |
| `/orchestrator-send` | `/or-send` |
| `/orchestrator-stop` | `/or-stop` |
| list/status/help/about/doctor/watch/attach helpers | `/or-dashboard` keyboard actions |
| supervisor/restart helpers | CLI or `tmux_orchestrator` model tool |

Dashboard controls: arrows or `j`/`k` select; Enter watches/attaches from inside
tmux; tmux prefix then `L` returns to Pi. `d` runs doctor on demand, `r` refreshes,
`x` separately confirms exact-session stop, `?` shows help, and `q`/Escape closes.
Opening it does not run doctor or background polling. Interactive send uses a
private file, not message text in arguments or metadata. Send follow-up only to
the waiting role owning the active assignment; cancellation acknowledgement is
not a final report.

## Profiles and exact per-project configuration

`economy`, `balanced`, and `thorough` remain deterministic thinking maps, not
provider/model selections; `thorough` is the compatibility default. Exact
per-run overrides win over canonical exact-project, user-global, and packaged
policy. Profiles cannot add writers, remove review, grant trust, or authorize
spend. Dynamic worker levels come only from each selected model's supported set.

Keep configuration outside target repositories. Existing canonical `directory`
mappings remain exact: no globs, parent matching, symlinked entries, credentials,
or endpoints. Custom specialists retain fixed trusted contracts and read-only
authority. See [profiles and project policy](https://github.com/revazi/pi-tmux-orchestrator/blob/v0.12.0/references/usage.md#profiles-and-exact-project-policy).

## Compatibility, safety, and known limits

- Python 3.11+, Node 22.19+, tmux 3.2+ (3.5+ recommended), macOS or Linux.
  Ordinary worker adapters have a Pi 0.87.1 compatibility baseline; enforcing
  admission is restricted to the reviewed Pi 1.4.0 boundary described above.
- Ordinary manifests remain v5, explicit custom-role manifests v7, and fresh
  dynamic manifests v10/v11 over `broker-v1`; older retained records remain
  readable. Broker schema 13 adds metadata-only admission state; legacy state
  does not silently enable enforcement.
- Request limits are 255 Choice options, 255 questions, 96 KiB request JSON, and
  224 KiB retained evidence. Approved pools remain at most 32 identities per pool
  and 100 distinct overall. Requests that cannot fit fail before HTTP; no tuple
  truncation, extra paid call, retry, or substituted plan is authorized.
- Immutable launch assignments remain authoritative, not model report prose.
  Provider Choice signals are not calibrated outcome confidence, hidden
  reasoning, model-quality evidence, billing, or savings evidence. Private task,
  guidance, report, credential, and provider bodies stay out of broker metadata.
- Call admission counts committed authorizations conservatively, not billed
  requests. Lost replies/cancellation do not refund grants. Catalog-derived
  `usage.cost` is not actual billed spend. Actual-cost enforcement and dynamic
  enforcing starts remain unavailable; the full #182 roadmap is not complete.
- Provider-free SDK/fetch, package, and tmux checks establish local mechanics,
  not production-wire acceptance. The earlier direct-Jev benchmark stopped on a
  failed preflight; this release does not authorize another live attempt or a
  default rollout. No paid provider probe is required for installing the package.

## Rollback

Finish or stop active runs first, then remove the new package, install the exact
prior **0.11.1** release, and restart Pi:

```sh
pi remove npm:pi-tmux-orchestrator
pi install npm:pi-tmux-orchestrator@0.11.1
```

Restore preserved prior configuration if needed. Do not resume in-flight runs
across versions or reuse newer active state with older runtime code. Keep the
original installation until its runs are safely finished or stopped. These are
operator instructions, not a claim of connected rollback verification. Review the
[0.11.1 release notes](https://github.com/revazi/pi-tmux-orchestrator/blob/v0.11.1/releases/v0.11.1.md).
