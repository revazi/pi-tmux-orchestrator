# Pi Tmux Orchestrator 0.9.0

Version 0.9.0 introduces a smaller dashboard-centered Pi command surface,
deterministic execution profiles, exact per-project user-global configuration,
and the token-efficiency work developed through the public roadmap.

## Breaking change: Pi slash commands

The extension now registers exactly five short commands. Duplicate long-form
commands and separate read-only helper commands have been removed.

| Before 0.9.0 | Use in 0.9.0 |
|---|---|
| `/orchestrator-dashboard` | `/or-dashboard` |
| `/orchestrator-models` | `/or-models` |
| `/orchestrator-start` | `/or-start` |
| `/orchestrator-send` | `/or-send` |
| `/orchestrator-stop` | `/or-stop` |
| list, status, help, about, doctor, watch, attach helper commands | `/or-dashboard`, then use its keyboard actions |
| supervisor and restart helper commands | `pi-tmux-agents` or the `tmux_orchestrator` model tool |

The dashboard controls are:

- arrows or `j`/`k`: select a session
- Enter: watch and attach to the exact selected session
- `x`: request the existing confirmed selected-session stop path
- `r`: refresh the session list
- `d`: explicitly run or hide current-project doctor
- `?`: help
- `q` or Escape: close

Opening or refreshing the dashboard does not run doctor or start background
polling.

## Upgrade safely

Finish or stop active orchestrations before updating so one run is not managed
by two installed package versions. Then update and restart Pi:

```bash
pi update npm:pi-tmux-orchestrator
```

Open `/or-dashboard`, press `?` to review the controls, and press `d` to validate
the current project and user-global configuration. Existing retained manifest
v1-v4 runs remain readable; newly started runs use manifest v5.

## Profiles

Packaged profiles change only deterministic Pi thinking levels:

| Profile | Implementer | Reviewer | Probe | Playwright | Django |
|---|---|---|---|---|---|
| `economy` | `medium` | `medium` | `low` | `medium` | `medium` |
| `balanced` | `high` | `high` | `medium` | `medium` | `medium` |
| `thorough` | `xhigh` | `high` | `high` | `high` | `high` |

`thorough` remains the compatibility default. These names are not provider-cost
or quality claims. Profiles cannot alter tools, authority, one-writer safety,
mandatory independent review, workflow routing, or budget behavior.

Select one profile for a run with CLI `--profile NAME` or the
`tmux_orchestrator` model tool's `profile` field. `/or-start` applies the exact
project mapping, user-global default, or packaged compatibility default. Up to
16 complete custom profiles may be defined in the strict user-global
configuration.

## Exact per-project configuration

Version-3 `~/.pi/agent/tmux-orchestrator.json` configuration supports up to 64
exact canonical project directories. For example:

```json
{
  "version": 3,
  "defaultProfile": "balanced",
  "profiles": {
    "review-heavy-economy": {
      "implementer": "medium",
      "reviewer": "high",
      "probe": "low",
      "playwright": "medium",
      "django": "medium"
    }
  },
  "projects": [
    {
      "directory": "/absolute/canonical/path/to/project",
      "profile": "review-heavy-economy",
      "implementationFlow": "phased",
      "specialists": ["probe"],
      "workspaceCapsule": false
    }
  ]
}
```

A project entry may also set exact provider/model defaults and per-role
overrides. Matching never uses globs, prefixes, implicit parents, repository
names, symlink components, or project-local policy. Project mappings cannot
grant trust, add writers, remove required review, force specialists, or provide
prompts or skills. Explicit run options take precedence over an exact project
mapping.

See the [README](https://github.com/revazi/pi-tmux-orchestrator/blob/v0.9.0/README.md#profiles-and-per-project-orchestration-configuration)
and [usage reference](https://github.com/revazi/pi-tmux-orchestrator/blob/v0.9.0/references/usage.md#profiles-and-exact-project-policy)
for the full schema and precedence rules.

## Other highlights

- A Pi-native running-orchestration dashboard with bounded metadata, explicit
  doctor, help/About, keyboard attach/watch, and confirmed stop.
- Strict project-selected `single` or `phased` implementation flows.
- Conservative deterministic activation for the built-in read-only probe,
  Playwright, and Django specialists, with explicit run overrides.
- Lean role-specific prompts, explicit digest-bound worker skills, bounded tool
  results, assignment usage accounting, retained analytics, and observational
  budget visibility.
- Optional bounded transient workspace capsules that do not replace governing
  `AGENTS.md`/`CLAUDE.md` discovery.
- Exact-artifact pre-release staging and isolated package acceptance.

Synthetic measurements in the repository remain proxies. This release makes no
provider-cost savings, quality-equivalence, or billing claim.

## Compatibility and safety

The mandatory built-in reviewer, one-writer implementer authority, project
instruction discovery, direct worker steering, authenticated broker transport,
metadata-only durable state, and confirmation requirements remain in place.
Custom-role lifecycle support is not included in 0.9.0.

## Rollback

If migration is blocked, finish or stop active 0.9.0 runs, remove the installed
package, install the previous exact version, and restart Pi:

```bash
pi remove npm:pi-tmux-orchestrator
pi install npm:pi-tmux-orchestrator@0.8.1
```

Report migration problems at
[GitHub Issues](https://github.com/revazi/pi-tmux-orchestrator/issues).
