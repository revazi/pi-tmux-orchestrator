# Pi Tmux Orchestrator 0.10.0

Version 0.10.0 is the next stable candidate after 0.9.5. It adds opt-in custom
read-only specialists, worker-context retention, repair-round continuation, a
watchable broker dashboard, and busy-database robustness. Control-plane
modularization from the closed #101 and #58 roadmaps is included.

## Breaking change

There is no protocol, command, configuration, database-schema, or
authority-model breaking change in 0.10.0. The 0.9 slash-command map still
applies: use `/or-dashboard`, `/or-models`, `/or-start`, `/or-send`, and
`/or-stop`. Retained older runs remain readable.

## Upgrade safely

Finish or stop active orchestrations before updating so one run is not managed
by two installed package versions. Then update and restart Pi:

```bash
pi update npm:pi-tmux-orchestrator
```

Open `/or-dashboard`, press `?` to review the controls, and press `d` to validate
the current project and user-global configuration. Start a new orchestration
after restarting. An already-running broker keeps the code loaded when that run
started and does not hot-reload this release.

Ordinary new runs still use manifest v5 and `broker-v1`. Explicit custom-role
runs use manifest v7. Version-3 user-global configuration remains accepted
without `customRoles`.

## Custom read-only specialists

Registered custom specialists are opt-in and remain read-only. They never
become writers, never replace the mandatory built-in reviewer, and never invent
IDs, tools, or contracts.

- Validate definitions with `pi-tmux-agents role-registry` before launch. The
  command does not start workers.
- Start through the normal confirmed flow: version-4 exact-project
  `customRoles`, CLI `--custom-role`, or an explicit dry-run preview.
- `/or-start` and the model tool include exact-project custom specialists from
  validated configuration unless cancelled or `projectCustomRoles` is false.
- `--no-project-custom-roles` omits the project list; explicit `--custom-role`
  wins. Provider and model values are always explicit.
- Thinking may be an exact level or `profile` to opt into the same identity's
  user-global custom-profile mapping. Profile mappings never select workers.
- Fresh registry and resource digest verification runs at selection and launch.
  Partial starts roll back exactly. Stale-generation and uncertain handovers
  fail closed.

See the [custom-role reference](https://github.com/revazi/pi-tmux-orchestrator/blob/v0.10.0/references/custom-roles.md).

## Worker context and repair continuation

Both features are opt-in and leave review authority and observational budgets
unchanged.

- Per-role `--worker-context ROLE=retain|prune`, `/or-start` worker-context
  input, or tool `workerContext` may retain provider context across assignment
  boundaries. Other roles keep default pruning. Retention can increase context
  cost.
- Retained roles may receive bounded worktree-metadata reuse hints. Those hints
  are not proof of current checks and do not authorize reused approval.
- `/or-start` additional repair-round input, `maxRepairRounds`, or CLI
  `start --max-repair-rounds N` sets an opt-in run-wide cap. Blank/omission
  disables the cap; `0` pauses before the first repair.
- The run remains incomplete at the cap. Explicit terminal CLI
  `continue SESSION --yes --command-id <32-hex-id>` authorizes one additional
  round. Continuation approval is operator-only.

## Broker dashboard

The broker pane is a metadata-only handoff view. It does not show task or
report bodies.

- A NOW flow line names the active worker, live phase, and waiting next role.
- Assignment-bound `worker_progress` is recorded only on phase change:
  thinking → streaming → tool → reporting.
- A bouncing `LIVE` activity bar shows motion. It is not task completion; a
  finished assignment is a report or handoff, not a full bar.
- Role and event glyphs have ASCII fallbacks.

Dashboard overlay controls are unchanged:

- arrows or `j`/`k`: select a session
- Enter: watch and attach to the exact selected session
- `x`: request the existing confirmed selected-session stop path
- `r`: refresh the session list
- `d`: explicitly run or hide current-project doctor
- `?`: help
- `q` or Escape: close

Opening or refreshing the dashboard does not run doctor or start background
polling.

## Profiles

Packaged profiles still change only deterministic Pi thinking levels:

| Profile | Implementer | Reviewer | Probe | Playwright | Django |
|---|---|---|---|---|---|
| `economy` | `medium` | `medium` | `low` | `medium` | `medium` |
| `balanced` | `high` | `high` | `medium` | `medium` | `medium` |
| `thorough` | `xhigh` | `high` | `high` | `high` | `high` |

`thorough` remains the compatibility default. These names are not provider-cost
or quality claims. Profiles cannot alter tools, authority, one-writer safety,
mandatory independent review, workflow routing, or budget behavior. Custom
profile mappings never create roles.

## Exact per-project configuration

Version-4 `~/.pi/agent/tmux-orchestrator.json` configuration supports exact
canonical project directories, including registered `customRoles`. Version 3
remains accepted without `customRoles`. For example:

```json
{
  "version": 4,
  "defaultProfile": "balanced",
  "projects": [
    {
      "directory": "/absolute/canonical/path/to/project",
      "profile": "thorough",
      "implementationFlow": "phased",
      "specialists": ["probe"],
      "workspaceCapsule": false,
      "customRoles": [
        {
          "id": "custom-security",
          "provider": "exact-provider",
          "model": "exact-model",
          "thinking": "low"
        }
      ]
    }
  ]
}
```

Matching never uses globs, prefixes, implicit parents, repository names,
symlink components, or project-local policy. Project mappings cannot grant
trust, add writers, remove required review, force specialists, or provide
prompts or skills. Custom role IDs must already exist in the user-global
registry. Explicit run options take precedence over an exact project mapping.

See the [README](https://github.com/revazi/pi-tmux-orchestrator/blob/v0.10.0/README.md#configure-orchestrations)
and [usage reference](https://github.com/revazi/pi-tmux-orchestrator/blob/v0.10.0/references/usage.md#profiles-and-exact-project-policy)
for the full schema and precedence rules.

## Other highlights

- Busy SQLite readers retry briefly, keep `status` readable, map concurrent
  custom-start admission to bounded `broker_not_ready` errors, and degrade
  Supervisor snapshot/usage to `temporarily-unavailable` without SQLite traces.
- The control plane is split into start, workflow, control, observer, and
  worker-support modules without changing broker-v1, review authority, or
  recovery behavior.
- Measured JavaScript test coverage and an identity-based Fallow health
  regression gate are included without adding package dependencies.

Synthetic measurements in the repository remain proxies. Isolated staged-package
actual-Pi startup and recovery acceptance remain distinct from generated custom
reports. This release makes no provider-cost savings, quality-equivalence, or
billing claim.

## Compatibility and safety

The mandatory built-in reviewer, one-writer implementer authority, project
instruction discovery, direct worker steering, authenticated broker transport,
metadata-only durable state, and confirmation requirements remain in place.
Custom specialists cannot write tracked files or skip review.

## Rollback

If migration is blocked, finish or stop active 0.10.0 runs, remove the installed
package, install the previous exact version, and restart Pi:

```bash
pi remove npm:pi-tmux-orchestrator
pi install npm:pi-tmux-orchestrator@0.9.5
```

Report problems through
[GitHub Issues](https://github.com/revazi/pi-tmux-orchestrator/issues).
